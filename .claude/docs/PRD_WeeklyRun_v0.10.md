# WeeklyRun - Product Requirements Document

## 1. 개요

### 1.1 프로젝트 정보
- **프로젝트명:** WeeklyRun
- **내부 애칭:** Weeky
- **버전:** v0.10
- **작성일:** 2025-01-22
- **작성자:** AI-Native 오케스트레이션 프로젝트

### 1.2 한 줄 요약
주간회의를 Weeky가 진행하고, 자동으로 회의록을 생성하는 서비스

### 1.3 네이밍 구조
| 구분 | 이름 | 용도 |
|------|------|------|
| 공식명 | **WeeklyRun** | PRD, 문서, Repo, 발표 자료 |
| 내부 애칭 | **Weeky** | UI 캐릭터, 팀 대화 ("Weeky 켤게요") |
| 실행 액션 | **WeeklyRun.run** | 회의 시작 버튼, 코드 시그니처 |

### 1.4 배경 및 문제 정의

**As-Is (현재 상황)**
- 매주 주간보고 회의에서 발언량 불균형 발생 (누구는 많이, 누구는 적게)
- 회의 중 방향을 잃고 산으로 가는 경우 있음
- 매번 다른 체계로 진행되어 일관성 부족
- 회의 종료 후 회의록 작성자의 부담 큼
- **Weeky 없이 진행한 회의도 수동으로 회의록 작성해야 함**

**To-Be (목표 상황)**
- AI가 질문 가이드를 제공하여 체계적인 회의 진행
- 모든 참석자가 주간업무록 기반으로 균등하게 발표
- 녹음 → STT → 자동 회의록 생성으로 후처리 부담 제거
- **녹음 파일만 있어도 회의록 자동 생성 가능**

### 1.5 핵심 가치
- **체계적 진행:** 소분류 단위 질문으로 누락 없는 업무 공유
- **시간 절약:** 회의록 자동 생성
- **일관성:** 매주 동일한 포맷과 흐름
- **유연성:** 실시간 회의 또는 녹음 파일 업로드 모두 지원

## 2. 사용자 및 환경

### 2.1 타겟 사용자
- **1차 (P1):** 제품기술팀 (5명) - 단일 팀
- **2차 (P2):** 동일 조직 내 다른 팀 (10명 이하) - 멀티 팀

### 2.2 사용 환경
- **회의 형태:** 대면 회의 (한 공간에 모임)
- **회의 주기:** 매주 화요일 14:00 (고정, 간헐적 변동 가능)
- **참석자:** 5명 고정 (연차 등으로 1-2명 불참 가능)
- **불참자 처리:** 주간업무록은 존재하나 회의 발표는 건너뜀
- **디바이스:** 데스크톱/노트북 브라우저 전용 (모바일 미지원)

### 2.3 회의 유형
| 유형 | 설명 | Phase |
|------|------|-------|
| 주간업무보고 | 인원별 순차 발표, 질문 가이드 제공 | P1 |
| 일반 회의 | 자유 토론 (데일리스크럼 등), STT 후 AI 정리 | P2 |

- 회의 시작 시 유형 선택 (복수 선택 가능)
- 복수 선택 시 드래그로 순서 변경 가능

### 2.4 회의 진행 방식
| 방식 | 설명 | Phase |
|------|------|-------|
| 실시간 회의 | Weeky와 함께 실시간 진행 + 녹음 | P1 |
| 녹음 파일 업로드 | 기존 녹음 파일로 사후 회의록 생성 | P1 |

## 3. Phase 구분

### 3.1 Phase 개요

| Phase | 범위 | 세션 |
|-------|------|------|
| **P1** | 단일 팀 + 주간업무보고 + 핵심 기능 + **녹음파일 업로드** | 세션 1 |
| **P2** | 멀티 팀 시스템 + 일반회의 모듈 + 잡담 필터링 | 세션 1 |
| **P3** | 스트리밍 STT + 서버 배포 + 슬라이드 생성 | 세션 2 (별도) |

> ⚠️ **중요:** P1과 P2는 한 세션에서 연속 실행. P3는 P1+P2 검증 후 별도 세션에서 진행.

### 3.2 개발 방법론: TDD (Test-Driven Development)

본 프로젝트는 **TDD 방식**을 적용한다.

**TDD 사이클:**
```
[Red] 실패하는 테스트 작성
    ↓
[Green] 테스트를 통과하는 최소한의 코드 작성
    ↓
[Refactor] 코드 개선 및 리팩토링
    ↓
(반복)
```

**TDD 적용 범위:**

| 영역 | TDD 적용 | 비고 |
|------|----------|------|
| Backend API | ✅ 필수 | 요청/응답 스펙 검증 |
| Backend 비즈니스 로직 | ✅ 필수 | Confluence 파싱, 회의록 생성 등 |
| Frontend 상태 관리 | ✅ 필수 | Jotai atoms, 회의 진행 로직 |
| Frontend UI 컴포넌트 | ⚠️ 선택 | 단순 렌더링은 생략 가능 |
| 오디오 녹음/재생 | ❌ 제외 | 수동 테스트로 대체 |

**테스트 유형:**

| 유형 | Backend (apps/api) | Frontend (apps/web) |
|------|-------------------|---------------------|
| 단위 테스트 | pytest | Jest |
| 통합 테스트 | pytest + TestClient | React Testing Library |
| E2E 테스트 | ❌ P1/P2 제외 | ❌ P1/P2 제외 |

**외부 API 테스트 전략:**
- **Confluence API**: 단위 테스트에서 모킹, 통합 테스트에서 실제 호출
- **Claude API**: 단위 테스트에서 모킹, 통합 테스트에서 실제 호출

### 3.3 코드 품질 기준

| 항목 | 기준 | 도구 |
|------|------|------|
| 테스트 커버리지 | **80% 이상** 유지 | pytest-cov, Jest --coverage |
| Lint | 오류 0건 | Biome (Frontend), Ruff (Backend) |
| 타입 체크 | 오류 0건 | TypeScript, mypy (선택) |
| 코드 포맷팅 | 자동 적용 | Biome (Frontend), Ruff (Backend) |
| 커밋 메시지 | Conventional Commits | commitlint |

### 3.4 기능 개발 완료 조건 (Definition of Done)

기능 하나가 개발 완료되려면 다음 조건을 **모두** 충족해야 한다:

| # | 조건 | 검증 방법 |
|---|------|----------|
| 1 | 테스트 작성 완료 | 해당 기능에 대한 단위/통합 테스트 존재 |
| 2 | 테스트 통과 | `mise test` 전체 통과 |
| 3 | 빌드 성공 | `mise build` 오류 없음 |
| 4 | Lint 통과 | `mise lint` 오류 0건 |
| 5 | 커버리지 유지 | 80% 이상 확인 |
| 6 | 커밋 완료 | Git에 기능 단위로 커밋 |

**검증 스크립트 (Backend - apps/api):**
```bash
#!/bin/bash
set -e

echo "=== Running Lint ==="
ruff check app/ tests/

echo "=== Running Tests with Coverage ==="
pytest --cov=app --cov-report=term-missing --cov-fail-under=80

echo "=== All checks passed! ==="
```

**검증 스크립트 (Frontend - apps/web):**
```bash
#!/bin/bash
set -e

echo "=== Running Lint ==="
pnpm lint

echo "=== Running Type Check ==="
pnpm type-check

echo "=== Running Tests with Coverage ==="
pnpm test --coverage --coverageThreshold='{"global":{"lines":80}}'

echo "=== Running Build ==="
pnpm build

echo "=== All checks passed! ==="
```

### 3.5 개발 순서 원칙

본 프로젝트는 **Backend 우선 개발** 방식을 따른다.

각 Phase 내에서 다음 순서를 준수:

```
Backend 개발 → Backend API 테스트 통과 → API 문서화 (OpenAPI) → Frontend 개발
```

Phase 간 전환 시:
```
P1 Backend 완료 → P1 API 테스트 → P1 OpenAPI 문서 → P1 Frontend → P1 통합 테스트
    ↓
P2 Backend 시작 → ...
```

###### STT 처리 단계 시각화

회의 종료 후 STT 처리 과정을 3단계로 시각화하여 사용자에게 진행 상황 전달:

**처리 단계:**
```
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│                    ┌──────────────────┐                         │
│                    │  🎀 Weeky        │                         │
│                    │  (thinking 표정)  │                         │
│                    │  "..."           │                         │
│                    └──────────────────┘                         │
│                                                                 │
│              회의록을 정리하고 있어요... (STT Processing)         │
│                                                                 │
│  ┌──────────────┬──────────────────────┬──────────────────┐    │
│  │ ✅           │ ⬜                    │ ⬜               │    │
│  │ Voice        │ Terminology          │ Formatting       │    │
│  │ Processing   │ Correction           │                  │    │
│  │ (음성 처리)   │ (용어 교정)           │ (포맷팅)         │    │
│  └──────────────┴──────────────────────┴──────────────────┘    │
│                                                                 │
│  ════════════════════════════════════▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒   │
│                        45%                                      │
│                                                                 │
│              잠시만 기다려주세요, 꼼꼼히 정리하고 있어요.          │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**3단계 설명:**

| 단계 | 이름 | 설명 | 예상 시간 |
|------|------|------|----------|
| 1 | Voice Processing | 녹음 파일 → 텍스트 변환 (STT) | 60% |
| 2 | Terminology Correction | 주간업무록 참조하여 용어 교정 | 25% |
| 3 | Formatting | 회의록 구조화 및 마크다운 생성 | 15% |

**UI 요소:**

| 요소 | 설명 |
|------|------|
| Weeky 표정 | `thinking` (생각 중) |
| 단계 표시 | 3개 박스, 완료된 단계는 ✅ 표시 |
| 프로그레스바 | 전체 진행률 표시 (Teal Gradient) |
| 메시지 | 단계별 안내 메시지 |

**단계별 메시지:**
- Voice Processing: "음성을 텍스트로 변환하고 있어요..."
- Terminology Correction: "주간업무록을 참조해서 용어를 교정하고 있어요..."
- Formatting: "회의록 형식으로 정리하고 있어요..."

**완료 시:**
- Weeky 표정: `thinking` → `done` → `happy`
- 메시지: "회의록 초안이 완성됐어요! 확인해주세요 📝"
- 자동으로 회의록 첨삭 화면으로 이동

**오류 시:**
- Weeky 표정: `thinking` → `sorry`
- 메시지: "처리 중 문제가 발생했어요 😢"
- [다시 시도] 버튼 표시

**🔑 핵심: 주간업무록 참조 기반 회의록 생성**

> **실시간 회의든 녹음 파일 업로드든 동일하게 적용**

주간업무록을 **참조 데이터**로 활용하여 회의록 품질 향상:

| 활용 방식 | 설명 | 예시 |
|----------|------|------|
| **용어 교정** | STT 오류를 주간업무록 용어로 교정 | "피육" → "P6" |
| **고유명사 인식** | 제품명, 프로젝트명 정확도 향상 | "한컴 어시" → "한컴어시스턴트" |
| **구조 매칭** | 발언 내용을 주간업무록 항목에 매칭 | 발언 → 해당 소분류에 배치 |
| **누락 감지** | 주간업무록에 있지만 언급 안 된 항목 표시 | "※ 언급되지 않음" 표시 |
| **맥락 보완** | 짧은 발언을 주간업무록으로 보완 | "완료했습니다" → 구체적 내용 추가 |

## 8. 데이터 모델

> DB 스키마는 P1부터 **멀티 팀 구조를 전제**로 설계.
> P1에서는 팀이 1개만 존재하고 선택 화면이 없을 뿐.
>
> **ORM**: SQLAlchemy (async) + Alembic (migration)
> **DB**: PostgreSQL 16 (로컬: Docker)

### 8.1 Team (팀)

```python
class Team(Base):
    __tablename__ = "teams"

    id: UUID = Field(primary_key=True, default=uuid4)
    name: str = Field(max_length=100, nullable=False, index=True)
    password_hash: str = Field(max_length=255, nullable=False)

    # Confluence 연동 설정 - P2에서 사용 (P1에서는 환경변수 사용)
    # API v2 기준: https://developer.atlassian.com/cloud/confluence/rest/v2/
    confluence_username: str | None = Field(max_length=200, nullable=True)  # Atlassian 계정 이메일
    confluence_token: str | None = Field(max_length=500, nullable=True)  # API 토큰 (암호화 저장 권장)
    confluence_space_id: str | None = Field(max_length=50, nullable=True)  # 스페이스 ID (v2는 key가 아닌 ID)
    confluence_report_parent_page_id: str | None = Field(max_length=50, nullable=True)  # 주간업무록 상위 페이지 ID
    confluence_report_title_pattern: str = Field(max_length=100, default="주간업무 (m/d)")
    confluence_minutes_parent_page_id: str | None = Field(max_length=50, nullable=True)  # 회의록 상위 페이지 ID
    confluence_minutes_title_pattern: str = Field(max_length=100, default="주간회의록 (m/d)")

    created_at: datetime = Field(default_factory=datetime.utcnow)
    updated_at: datetime = Field(default_factory=datetime.utcnow, onupdate=datetime.utcnow)

    # Relationships
    members: list["TeamMember"] = Relationship(back_populates="team")
```

### 9.5 로딩 UI

> **원칙:** Weeky 표정으로 감정적 상태를 전달하고, 프로그레스바로 정확한 진행률을 표시

| 화면 | 트리거 | Weeky 표정 | 프로그레스 | 메시지 |
|------|--------|-----------|-----------|--------|
| 대시보드 | 회의 목록 로드 | - | 스켈레톤 | - |
| 회의 준비 | Confluence 연동 | `thinking` | 스피너 | "주간업무록을 불러오고 있어요..." |
| 녹음 파일 업로드 | 파일 업로드 | `tip` | 프로그레스 바 (%) | "파일을 업로드하고 있어요..." |
| STT 처리 | 음성 → 텍스트 | `thinking` | 3단계 + 프로그레스 바 | 단계별 메시지 |
| 회의록 생성 | AI 생성 | `thinking` | 스피너 | "회의록을 작성하고 있어요..." |
| 회의록 저장 | Save Draft | `tip` | 버튼 내 스피너 | - |
| Confluence 업로드 | Upload | `tip` → `trophy` | 버튼 내 스피너 → 완료 | "업로드 완료!" |

## 12. 사용자 시나리오

### 10.1 P1 정상 흐름 - 실시간 회의 (Happy Path)

**1. 회의 전 (5분)**
1. WeeklyRun 접속 → 팀 대시보드 표시
2. [+ 새 회의 시작] 클릭
3. **[🎤 실시간 회의] 선택**
4. Confluence 주간업무록 자동 감지 (또는 URL 입력)
5. 참석자 체크, 발표 순서 확인/조정
6. [▶ WeeklyRun.run] 클릭

**2. 회의 중 (30-60분)**
1. 녹음 자동 시작
2. 첫 번째 발표자 화면 표시
3. 발표자: 왼쪽 패널 보며 발표
4. [다음 항목] 또는 [이 사람 완료] 클릭
5. 모든 참석자 완료
6. [회의 종료] 클릭

**3. 회의 후 (5-10분)**
1. 녹음 파일 → STT 처리 (진행 상황 표시)
2. AI 초안 생성 (주간업무록 참조) → auto_draft 자동 저장
3. 회의록 첨삭 화면 표시
4. 오타 수정, 내용 보완
5. [Save Draft] 또는 [Upload to Confluence]

### 10.2 P1 정상 흐름 - 녹음 파일 업로드 (Happy Path) (NEW)

**1. 설정 (3분)**
1. WeeklyRun 접속 → 팀 대시보드 표시
2. [+ 새 회의 시작] 클릭
3. **[📁 녹음 파일 업로드] 선택**
4. 회의 유형 선택 (주간업무보고 체크)
5. Confluence 주간업무록 연동
6. 참석자 체크
7. 녹음 파일 업로드 (mp3/wav/webm/m4a)
8. [회의록 생성 시작] 클릭

**2. 처리 (5-10분)**
1. 녹음 파일 → STT 처리 (진행 상황 표시)
2. AI 초안 생성 (주간업무록 참조하여 용어 교정) → auto_draft 자동 저장
3. 회의록 첨삭 화면 표시

**3. 완료 (5분)**
1. 오타 수정, 내용 보완
2. [Save Draft] 또는 [Upload to Confluence]

### 10.3 예외 흐름

**Confluence 연결 실패:**
1. 오류 메시지 표시
2. URL 직접 입력 또는 내용 붙여넣기 옵션 제공

## 16. Confluence API v2 연동 상세

### 16.1 API 개요

| 항목 | 값 |
|------|-----|
| API 버전 | **v2** (최신) |
| 문서 | https://developer.atlassian.com/cloud/confluence/rest/v2/ |
| 인증 | Basic Auth (email + API token) |
| Content-Type | `application/json` |

### 16.2 주요 엔드포인트

**페이지 생성 (회의록 업로드):**
```
POST /wiki/api/v2/pages
```

**페이지 조회 (주간업무록 읽기):**
```
GET /wiki/api/v2/pages/{page-id}
GET /wiki/api/v2/spaces/{space-id}/pages  # 스페이스 내 페이지 목록
```

**페이지 검색 (제목으로 찾기):**
```
GET /wiki/api/v2/pages?space-id={space-id}&title={title}
```

### 16.3 페이지 생성 요청 예시

```json
{
  "spaceId": "123456",
  "status": "current",
  "title": "주간회의록 (1/21)",
  "parentId": "987654321",
  "body": {
    "representation": "storage",
    "value": "<p>회의록 내용...</p>"
  }
}
```

| 필드 | 설명 | 매핑 |
|------|------|------|
| `spaceId` | 스페이스 ID | `CONFLUENCE_SPACE_ID` 또는 `team.confluence_space_id` |
| `title` | 페이지 제목 | `confluence_minutes_title_pattern` 기반 생성 |
| `parentId` | 상위 페이지 ID | `CONFLUENCE_MINUTES_PARENT_PAGE_ID` 또는 `team.confluence_minutes_parent_page_id` |
| `body.value` | 페이지 내용 | Markdown → Storage format 변환 |
| `body.representation` | 콘텐츠 형식 | `storage` (Confluence 내부 형식) |

### 16.4 인증 헤더

```python
import base64

credentials = f"{username}:{token}"
encoded = base64.b64encode(credentials.encode()).decode()

headers = {
    "Authorization": f"Basic {encoded}",
    "Content-Type": "application/json",
    "Accept": "application/json"
}
```

### 16.5 Markdown → Storage Format 변환

Confluence는 자체 Storage format (XHTML 기반)을 사용하므로 Markdown 변환 필요:

| Markdown | Storage Format |
|----------|----------------|
| `# 제목` | `<h1>제목</h1>` |
| `**굵게**` | `<strong>굵게</strong>` |
| `- 항목` | `<ul><li>항목</li></ul>` |
| `\| 표 \|` | `<table>...</table>` (ac:structured-macro) |

> **구현 참고:** `markdown` 라이브러리 + 커스텀 변환 또는 `atlassian-python-api` 사용
